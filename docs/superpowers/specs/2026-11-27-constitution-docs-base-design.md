# L0 宪法精简 + docs/base 活文档 设计

日期：2026-11-27
状态：待审

## 1. 意图与背景

L0 宪法（`content/L0-constitution/AGENTS.base.md`）在迭代中偏离了用户原稿：加入了与 superpowers 流程技能重复的门禁（阶段审批、完结自检），把"按 Plan 规模选择执行方式"改成了"强制派发子代理"，把"主动提出关键点"改成了"一次性列出所有假设"，并把产品设计并入交互条款。

同时"文档即契约"规定的 `docs/00-plans/` + `docs/01-biz`~`05-deploy` 与 superpowers 产出的 `docs/superpowers/{specs,plans}/` 冲突——AI314 仓库自身就没遵守前者。

本次要做的：

1. 宪法回到原稿意图，只写 AI314 独有的约束；流程交给 superpowers，宪法只叠加约束。
2. 文档分成两类且各司其职：
   - **特性片段** `docs/superpowers/`：编码前的契约（spec/plan），不动。
   - **项目活文档** `docs/base/`：项目全局、始终反映当前真实状态，特性完成时回写。
3. 新增工具技能 `ai314:docs-base-sync` 负责存量盘点与特性回写。

## 2. 目标 / 非目标 / 反目标

**目标**
- 宪法条款与原稿逐条对应，删除与流程技能重复、或用户不确定的内容。
- 明确优先级与"宪法 vs 流程技能"的分工，消除 `ai314:planning` 被 superpowers 跳过的风险。
- `docs/base/` 结构固定、按需创建，Agent 不需要猜路径。

**非目标**
- 不修改 superpowers 插件或其文档路径。
- 不改 L1 stack 的技术内容（只修引用）。
- 不改构建器/适配器逻辑。

**反目标（技术上完成但算失败）**
- 宪法变长或变得更像流程说明书。
- `docs/base/` 被写成特性变更日志（那是 superpowers spec 的职责）。
- onboard 给小项目一次性铺一堆空文档。

## 3. 已定决策（用户确认）

- `docs/superpowers/` 保持 superpowers 默认路径，不迁移。
- 活文档目录为 `docs/base/`，单层、文件名固定大写：`PRODUCT.md`、`ARCH.md`、`UI.md`、`API.md`、`DEPLOY.md`。
- 活文档在**特性完成时回写**，编码前的契约由 superpowers spec 承担。
- 新技能命名 `ai314:docs-base-sync`。
- 宪法不确定的内容先拿掉。

## 4. 宪法新稿（替换 `AGENTS.base.md` 全文，保留末尾索引占位符）

> 以下为定稿措辞草案，实现时可做文字润色，但条款数量、编号、含义不得改变。

```md
# AI314 工程宪法

## 零、 加载与优先级（最高优先级）

- **技能路由**：项目根 `AGENTS.md` 中 `<!-- AI314:BEGIN -->` ~ `<!-- AI314:END -->` 声明块按路径启用 stack / mode，改动对应路径前必须先加载对应技能（`ai314:<技能名>`）。未声明时，按文末《已挂载技能索引表》的触发条件加载。
- **优先级**：用户当次指令 > 项目 `AGENTS.md` > 已启用 `mode-*` 的豁免条款 > 本宪法 > 流程技能（如 superpowers）的默认值。**第 14 条安全底线不可豁免。**
- **与流程技能协作**：头脑风暴、计划、执行、审查的流程由流程技能驱动，本宪法只叠加约束。编写 spec / plan 时**同时加载** `ai314:planning`；审查代码或宣告完成前**同时加载** `ai314:code-review`。

## 一、 产品与交互

1. **产品设计**：遵循奥卡姆剃刀，给用户最直觉、有经验的产品体验（UI、CLI、API 皆然），规避冗长、反流程的设计。
2. **交互设计**：优先采用业界前沿通用标准（UI 设计、产品美学、交互体验、快捷键）；禁止未经确认引入新页面 / 多级弹窗，默认单屏直达；视觉与组件严格复用项目既定 Design Token / UI 库，禁止自由发挥样式。

## 二、 架构与代码

3. **架构设计**：分层 + 模块化目录；在 KISS 前提下权衡后续扩展性与可维护性，禁止过度设计（YAGNI）。**单文件不超过 300 行，单函数不超过 50 行，禁止跨层直接调用与循环依赖；超限时先拆分再继续加功能。**
4. **最小变更**：严格 Minimal Diff。未经明确指令，严禁修改现有公开接口（API / Schema / CLI 参数，以 `docs/base/API.md` 为准）的签名与字段结构，严禁顺手重构无关文件。
5. **依赖选型**：优先语言标准库与项目现有依赖；新增第三方依赖前，先核对依赖清单与锁文件（`go.mod`/`go.sum`、`package.json`/lock、`Cargo.toml`/`Cargo.lock` 等）确认兼容，并在 spec / plan 中声明理由。
6. **注释**：尽量一句话说清楚，解释 Why（业务意图 / 踩坑原因）而非 What，限 1~3 行；对外暴露的模块 / 接口保留标准类型签名与入参出参说明。

## 三、 协作与文档

7. **可视化确认**：与用户确认决策点（业务流程、产品功能、UI 布局、技术架构、项目目录、模块设计）时，优先用 Web HTML 交互，不必在意 token 用量。草稿放 `docs/_drafts/` 或 `.superpowers/`（均加入 `.gitignore`），确认后结论写入 spec。
8. **文档即契约**：
   - 特性契约：编码前的 spec / plan 由流程技能产出（如 `docs/superpowers/`）。
   - 项目活文档：`docs/base/` 下 `PRODUCT.md`（业务与产品）、`ARCH.md`（架构、目录布局、组件与技术选型）、`UI.md`（UI 选型与交互规范）、`API.md`（公开接口契约）、`DEPLOY.md`（环境、构建、发布、运维），按需创建，始终反映项目当前真实状态。
   - 特性完成、合并前用 `ai314:docs-base-sync` 增量回写受影响段落，禁止全量重写；单篇超 300 行拆为同目录 `<名>-<模块>.md`，原文件保留为索引。
   - `README.md` 只保留项目核心介绍、上手方式与文档地图。
9. **主动提示与默认值先行**：头脑风暴 / 计划阶段，主动提出用户未提及但实施中必须关注的要点，超出能力范围的事主动告知。区分"不可逆决策"与"可逆细节"：前者必须中断确认；后者直接采用行业最佳实践落地，并在交付说明中标注"已默认采用 X，如需调整请告知"。
10. **模型与执行方式**：架构设计 / 头脑风暴用高阶模型，子代理执行用常规高性价比模型；Plan 执行阶段按 Plan 规模推荐采用子代理驱动或当前会话执行。

## 四、 质量与安全

11. **脚本化**：构建、部署、测试、Proto 编译、配置替换等重复流程，优先封装为 `Makefile` / shell / python / go 命令。
12. **根因与验证闭环**：复现 → 抓证据（日志 / 报错堆栈 / 截图）→ 定位根因 → 写失败用例 → 修复 → 跑通验证。严禁盲改试错和 try-catch 吞异常掩盖错误。
13. **TDD 2/8 原则**：测试聚焦核心主链路与关键边界（空值 / 超时 / 并发）；**严禁修改断言或硬编码返回值骗过测试。**
14. **安全底线**：票据、密钥、Token 一律通过环境变量注入，`.env*` 必须加入 `.gitignore`，严禁硬编码进代码或文档。
```

## 5. 技能改动

### 5.1 `ai314:planning`（`content/L0-constitution/skills/planning/SKILL.md`）

定位不变："只规定计划里必须写进什么，不规定流程"。改动：

- 删除 `docs/00-plans/` 与"第 3 节门禁"；spec/plan 位置交给流程技能。
- 条款编号全部按新宪法更新。
- 计划必须包含（新增项加粗）：
  - 每个任务的 `约束`（宪法条款号 + stack/mode 红线）与 `自检命令`（取自 stack 第 4 节）。
  - 新增依赖声明（第 5 条）。
  - **公开接口变更清单**（第 4 条）：列出将改动的 API/Schema/CLI，逐项待用户确认；无则写"无"。
  - **`docs/base/` 影响清单**（第 8 条）：列出完成时需回写的文件与段落；无则写"无"。
  - 测试策略（第 13 条）、脚本化（第 11 条）、执行方式推荐（第 10 条）。
- 开工前：加载 stack/mode；主动提示关键点与默认值（第 9 条）；决策点用 HTML 草稿（第 7 条）。

### 5.2 `ai314:code-review`（`content/L0-constitution/skills/code-review/SKILL.md`）

- 检查表条款号按新宪法更新；删除旧 §3 "同步更新 docs" 的写法。
- 新增/调整检查点：
  - 第 3 条：给出客观测量方式（如 `wc -l` 统计改动文件行数），不凭目测。
  - 第 4 条：以 `docs/base/API.md`（存在时）判断是否触碰公开接口。
  - 第 8 条：`docs/base/` 影响清单中的文件是否已回写；README 文档地图是否需更新。
  - 已启用 `mode-legacy-maintenance` 时，核心函数修改是否有特征测试。
- 严重度定义：
  - **Critical**：违反第 14 条、未经确认改公开接口（第 4 条）、篡改断言 / 硬编码骗测试（第 13 条）。
  - **Important**：其余条款违反。
  - **Minor**：注释、风格类。
- 输出格式不变；"附实际运行命令"保留（属于审查输出格式，非宪法条款）。

### 5.3 新增 `ai314:docs-base-sync`（`content/tools/docs-base-sync/SKILL.md`）

frontmatter `name: docs-base-sync`，description 覆盖两种触发：存量项目缺少/过期 `docs/base/` 时盘点；特性完成、合并前回写。

**模式 A：存量盘点**
1. 分析代码、配置、构建脚本、部署文件、已有 README / docs，推断当前产品、架构、目录布局、组件选型、公开接口、部署方式。
2. 只为项目实际存在的主题生成文件（无 UI 不建 `UI.md`，无对外接口不建 `API.md`）。
3. 推断不确定处标注 `> 待确认：…`，不臆造。
4. 先把拟写内容（文件清单 + 每篇大纲）给用户确认，再写入。
5. 更新 `README.md` 的文档地图（只增改地图段落，不重写 README）。

**模式 B：特性回写**
1. 输入：本次特性的 spec/plan（含 `docs/base/` 影响清单）与分支 diff。
2. 只增量修改受影响段落，禁止全量重写；记录的是"现在是什么"，不是"这次改了什么"。
3. 超 300 行按第 8 条拆分。
4. 回写内容随特性一起提交。

**各文件建议大纲**（技能内给出，作为默认值）：
- `PRODUCT.md`：定位与用户、核心功能、关键业务流程、术语表。
- `ARCH.md`：架构图（mermaid）、分层与模块职责、目录布局、组件与技术选型及理由、数据存储。
- `UI.md`：UI 框架与组件库、Design Token、页面清单、交互规范与快捷键。
- `API.md`：公开 API / Schema / CLI 参数清单与兼容性约定。
- `DEPLOY.md`：环境清单、构建与发布命令、配置与密钥注入方式（只写变量名，不写值）、运维要点。

与 `ai314:extract-stack` 的区别：后者提炼可复用的技术栈经验回流 AI314；本技能记录本项目现状，留在项目内。
