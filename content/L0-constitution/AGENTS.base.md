# VibeCoding 工程协作宪法

## 零、 技能路由与按需加载铁律（最高优先级）

在进入 `Brainstorming`、`Writing-Plans` 或修改特定目录代码前，**必须根据文末《已挂载技能索引表》的触发条件，优先读取对应路径的 `SKILL.md` 规范**，严格遵循其钦定技术栈、目录拓扑与红线约束，禁止跳过规范自行重新做技术调研。

- **技能命名**：本宪法与项目声明块中的技能均以 `ai314:<技能名>` 表示（如 `ai314:stack-go-microservice`），在 Claude Code 与 Antigravity 中均可按此名调用。
- **项目声明块**：项目根 `AGENTS.md` 中 `<!-- AI314:BEGIN -->` ~ `<!-- AI314:END -->` 之间的表格声明了按路径启用的 stack / mode，改动对应路径前必须先加载对应技能。
- **优先级**：声明块启用的 `mode-*` 技能中的豁免条款优先于本宪法对应条款；**第 15 条安全底线不可豁免**。

## 一、 工作流门禁与协作机制

1. **阶段隔离与审批门禁**：严格执行“调研/头脑风暴 → 计划确认 → 编码实现 → 独立审查”流水线。**在获得用户对 HTML 原型或 Plan 的明确 `Approved` 确认前，严禁修改业务源码。**
2. **可视化对齐（HTML 优先）**：涉及业务流程、UI 布局、目录结构或架构选型确认时，优先生成单文件交互式 HTML（输出至 `docs/_drafts/`），确认后沉淀为正式 MD 文档并清理草稿。
3. **文档即契约**：正式设计沉淀至 `docs/`（`00-plans/` 存放执行计划，`01-biz/`、`02-prod/`、`03-ui-design/`、`04-arch/`、`05-deploy/`）。编码前先增量更新对应 MD 变更点，禁止全量重写。
4. **前置澄清与默认值先行**：在 Brainstorming / Plan 阶段，一次性列出所有**不可逆的模糊假设**及**能力边界风险**供用户确认；对于可逆的实现细节（如分页大小、常规超时），直接采用行业最佳实践作为默认值落地，并在交付时标注。
5. **模型路由与上下文隔离**：高阶模型负责需求拆解、SPEC 定稿与关键架构评审；常规模型负责 Plan 拆解与 Subagent 编码执行。多文件并行改造或独立模块调研强制派发 Subagent，并通过 `docs/00-plans/` 实时外置状态以支持随时新开干净会话。

## 二、 产品、架构与代码红线

6. **直觉化产品与交互**：遵循奥卡姆剃刀原则，默认采用单屏直达交互，禁止未经确认引入新页面或多级弹窗；UI 严格复用项目既定 Design Token 与组件库，禁止自由发挥样式；桌面/Web 端优先补齐主流快捷键。
7. **架构与物理复杂度上限**：采用分层 + 模块化设计，遵循 KISS 与 YAGNI 原则，严禁过度抽象。**单文件不超过 300 行，单函数不超过 50 行，严禁跨层直接调用与循环依赖。**
8. **最小变更半径**：严格执行 Minimal Diff。未经明确指令，严禁修改现有公开接口（API / Schema / CLI 参数）的签名与字段结构，严禁顺手重构无关文件。
9. **技术依赖白名单**：优先使用语言标准库及项目现有依赖；新增任何第三方依赖前，必须先核对本地锁文件（`package.json` / `go.mod` / `Cargo.toml` 等）确认兼容性，并在 Plan 中声明理由。
10. **高信噪比注释**：行内注释仅解释 `Why`（业务意图/踩坑原因）而非 `What`（代码字面意思），限 1~3 行；对外暴露的模块/接口必须保留标准类型签名与入参出参说明。

## 三、 质量门禁、自动化与安全

11. **根因与证据链闭环**：修复 Bug 必须遵循“复现 → 抓取日志/报错堆栈 → 定位根因 → 写失败用例 → 治本修复”链路，严禁盲猜试错或用 `try-catch` 吞异常。**任何“已完成/已修复”的汇报，必须附带实际运行的测试/编译命令及通过摘要。**
12. **2/8 原则 TDD 纠偏**：测试用例聚焦核心业务主链路（Happy Path）与关键边界异常（空值/超时/并发），避免低效发散；**严禁通过篡改预期断言或硬编码返回值来“骗过”测试。**
13. **重复操作脚本化**：构建、测试、部署、Proto 编译、配置替换等重复流程，统一封装为 `Makefile` 或 `scripts/` 下的标准命令。
14. **完结自检门禁**：向用户宣告任务完成前，必须自动执行项目 Lint、静态类型检查与核心测试脚本并确保全绿。
15. **安全底线**：任何密钥、Token、凭证一律通过 `.env` 环境变量注入，且必须确保 `.env*` 已加入 `.gitignore`，严禁硬编码进代码或文档。
