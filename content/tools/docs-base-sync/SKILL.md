# AI314 活文档盘点与回写

`docs/base/` 是项目的**活文档**：描述项目"现在是什么样"，始终反映当前真实状态（宪法第 8 条）。特性的"为什么改、怎么改"属于 spec / plan，不写进这里。

| 文件 | 内容 | 何时创建 |
| :-- | :-- | :-- |
| `PRODUCT.md` | 业务与产品 | 总是 |
| `ARCH.md` | 架构、目录布局、组件与技术选型 | 总是 |
| `UI.md` | UI 选型、Design Token、交互规范 | 有用户界面时 |
| `API.md` | 公开 API / Schema / CLI 参数契约 | 有对外接口时 |
| `DEPLOY.md` | 环境、构建、发布、运维 | 有部署或发布流程时 |

## 模式 A：存量盘点

适用于没有 `docs/base/`、或文档已明显过期的项目。

1. 分析代码目录、依赖清单、配置、构建脚本（Makefile / scripts）、部署文件（Dockerfile / CI / k8s）、已有 README 与 docs，推断产品定位、架构、目录布局、组件选型、公开接口、部署方式。
2. 只为项目实际存在的主题生成文件，不建空文件。
3. 推断不确定处写 `> 待确认：…`，不臆造；不写密钥值，只写变量名。
4. **先把文件清单与每篇大纲给用户确认**，确认后再写入。
5. 更新 `README.md` 的文档地图：只增改地图段落，不重写 README 其余内容。

## 模式 B：特性回写

适用于特性完成、合并前。

1. 读本次特性的 spec / plan（含 `docs/base/` 影响清单）与分支 diff（`git diff <基线>...HEAD`）。
2. 只增量修改受影响段落，禁止全量重写；写"现在是什么"，不写"这次改了什么"。
3. 影响清单之外若发现文档与代码不一致，列出给用户确认后再改。
4. 回写内容与特性代码同一分支提交。

## 拆分规则

单篇超过 300 行时，拆为同目录 `<名>-<模块>.md`（如 `ARCH-data.md`），原文件保留概述并作为索引链接各分篇。目录始终保持一层。

## 各文件建议大纲（默认值，可按项目调整）

- **PRODUCT.md**：定位与目标用户；核心功能清单；关键业务流程；术语表。
- **ARCH.md**：架构图（mermaid）；分层与模块职责；目录布局；组件与技术选型及理由；数据模型与存储。
- **UI.md**：UI 框架与组件库；Design Token；页面清单；交互规范与快捷键。
- **API.md**：公开 API / Schema / CLI 参数清单；版本与兼容性约定；变更须经确认（宪法第 4 条）。
- **DEPLOY.md**：环境清单；构建与发布命令；配置与密钥注入方式（只写变量名）；监控与运维要点。

## 与 `ai314:extract-stack` 的区别

`extract-stack` 提炼可复用到其他项目的技术栈经验，回流 AI314；本技能记录**本项目**现状，留在项目内。
